# Languages

The site publishes **English only**. This document exists so that adding a language is a
decision about translation, not about architecture.

Nothing here is switched on. `LOCALES` in `src/lib/i18n.ts` has one entry, and every function
that would branch on locale currently returns the English answer. The point of doing this work
now was that the expensive parts — deciding where strings live, what the URLs look like, how
content gets a second version — get harder with every component added, and the cheap parts
can wait.

---

## The two halves

**Interface text** — button labels, headings, error messages, anything the site writes about
itself. Lives in `src/i18n/en.ts`, read through `t()`.

**Content** — town blurbs, café notes, event descriptions, articles. Lives in the database,
written by a person, translated through the `translations` table.

The test is *"did an author write it, or did the interface?"* Get this wrong in either
direction and you end up either translating the same sentence in forty places, or storing
button labels in Postgres.

---

## Interface text

```ts
import { t } from "@/i18n";

t("nav.towns")                               // "Towns"
t("town.ranked", { rank: 4 })                // "#4 ranked"
t("rankings.title", { total: 104, ranked: 18 })
```

Keys are checked at compile time — a typo will not build. A key that somehow resolves to
nothing renders as the key itself (`town.missingThing`), which is a bug you notice in a
second; an empty string is one you ship.

**Never build a sentence by joining fragments.** `t("a") + town + t("b")` is untranslatable,
because word order differs by language. Use a placeholder and pass the value.

### Extraction is unfinished, on purpose

`SiteNav` is fully converted and is the reference. Roughly 230 visitor-facing strings across
the rest of the pages and components are still inline. That is deliberate: the catalogue,
the accessor and the pattern are the parts that needed deciding; moving the remaining strings
is mechanical and can happen a file at a time, or in one sitting, whenever it is worth doing.

Find what is left:

```bash
grep -rnE '>[A-Z][a-z][^<>{}]{12,}<' src/app src/components \
  --include=*.tsx --exclude-dir=admin
```

**The admin is out of scope and should stay that way.** It has one user.

## Content

`translations` (migration 0020) holds one row per translated field:

| table_name | row_id | column_name | locale | value | source |
|---|---|---|---|---|---|
| towns | bright | blurb | de | Bright liegt… | reviewed |

Nothing reads it yet. When something does, a missing row falls back to the English column —
so a half-translated locale degrades to English rather than to blank space.

The `source` column distinguishes `machine`, `reviewed` and `human`. This is not
bureaucracy. The site's whole position is that it does not claim what it cannot back up, and
a machine-translated sentence asserting a café is verified bike-friendly is a claim nobody
has checked. Machine translation is a fine starting point for interface text. For anything a
reader would take as local knowledge, it needs a human who rides.

## Adding a language

1. **Decide it is worth it.** Each language is a permanent tax on content velocity: every new
   town, event and article needs doing again, forever. At 100 towns and 33 events, one extra
   language roughly doubles the content records you maintain. Add one when there is a reason —
   a tourism board deal, a partner, or traffic showing demand — not to look international.

2. `src/i18n/de.ts`, satisfying the `Messages` type. Missing keys will not compile, which is
   the point.

3. Add the locale to `LOCALES`, `LOCALE_NAMES` and `HTML_LANG` in `src/lib/i18n.ts`, and to
   `CATALOGUES` in `src/i18n/index.ts`.

4. Move the routes under a `[locale]` segment: `src/app/**` becomes `src/app/[locale]/**`.
   This is the one genuinely invasive step and it was deliberately deferred — it is mechanical
   (a move plus threading `params.locale`), it does not get much worse with time, and doing it
   before a second language existed would have added a layer with nothing on the other side of
   it. `localePath()` already assumes the default locale keeps bare URLs, so
   `/towns/bright` never moves and nothing that links to it breaks.

5. Translate the content into `translations`, then set `published = true` in `locales`.

`hreflang` and the sitemap need no work — `alternatesFor()` and `src/app/sitemap.ts` both
emit alternates automatically once `LOCALES` has more than one entry.

### Which language first

German, and it is not close. The ADFC's 2025 analysis puts 39.3 million Germans cycling on
holiday or leisure and €40 billion of economic impact from one country, against the ECF's
€44 billion for the whole EU. German cycle tourists spend €133–144 a day. With Austria and
Switzerland that is about 100 million people in one language.

Caveat worth remembering: German cycle tourism is mostly *touring* — rail trails, e-bikes,
multi-day routes — while these guides are performance destinations. The headline figure
flatters the fit.

After German: French, Spanish, Dutch. Then Italian, Japanese, Traditional Chinese and Korean,
each of which maps to towns already covered.

**The supply side may want a different order.** Riders read German first; the businesses being
signed in Girona, Mallorca and Hualien read Catalan, Spanish and Mandarin. Translating the
partner pack and the claim-your-listing flow is a far smaller job than translating the guides,
and may be worth doing first.

## Search visibility

Related, and fixed at the same time, because the two share a mechanism.

The site had **no `sitemap.xml` and no `robots.txt`**. Google could only find a town guide by
crawling a link to it from a page it had already found — slow and unreliable for a new domain
with few inbound links, and the usual reason Search Console reports pages as *discovered* or
*crawled — currently not indexed*.

- `src/app/sitemap.ts` — built from live content, so a town added in the admin appears without
  anyone remembering. Currently 167 URLs.
- `src/app/robots.ts` — allows the site, excludes API routes, the admin, and personal pages.
- Canonical URLs on every page, explicit on town, event and article pages.

`/subscribed`, `/unsubscribed` and `/admin` carry `noindex` deliberately and will always
appear in Search Console as excluded. That is correct, not a fault.

After deploying, submit `https://cycletowns.com/sitemap.xml` in Search Console →
Sitemaps. Indexing takes days to weeks; a new site with few inbound links will not be indexed
quickly no matter how clean the sitemap.
